# Tree of Thoughts

Файл ведёт OpenCode по вашим запросам. Агент записывает фактические результаты экспериментов и вносит изменения в связанные файлы. Свою оценку сообщайте ему в чате; вручную заполнять шаблон не нужно.

- Артефакт Практики 1: `practices/practice_01/problem.md`, раздел «Метрики».
- Модель: VseLLM / openai/gpt-5.
- Цель: найти лучший способ оформить раздел «Метрики», не меняя смысл M1 и M2.

## Варианты (наблюдаемые плюсы/минусы)

А) Текущая компактная таблица

- Плюсы:
  - Компактно: один блок правил + единая таблица.
  - Не меняет содержание и согласованные правила/цели.
  - Понятные источники и момент измерения уже указаны.
- Минусы:
  - «Baseline» и «после улучшения» не разделены явными колонками (нужно следить, чтобы их не смешивать в ячейках).
  - Для читателя неочевидно, куда помещать результат P1-02 (в тексте/примечании или в таблице).

B) Отдельный блок для каждой метрики (определение, формула, baseline, цель, источник, момент измерения)

- Плюсы:
  - Максимальная однозначность: у каждой метрики свои подпункты (легче читать и ссылаться).
  - Воспроизводимость: шаги и источники рядом с определением.
- Минусы:
  - Менее компактно: дублирование заголовков/подпунктов, раздел растягивается.
  - Для текущего учебного кейса может выглядеть избыточно (две метрики, простые правила).

C) Таблица с отдельными колонками «Baseline (P1-01)» и «После улучшения (P1-02)»

- Плюсы:
  - Явно исключает смешение baseline и результата: отдельные колонки.
  - Улучшает воспроизводимость: видно, где брать значения до и после (ссылки на файлы результатов).
  - Остаётся достаточно компактной в сравнении с вариантом B.
- Минусы:
  - Немного шире таблица; требуется аккуратно формулировать для M2, чтобы не подменять оценку студента авто‑расчётом.

## Сравнение по критериям

- Однозначность подсчёта: B = C > A (B и C структурно снимают риск смешения; A требует дисциплины оформления).
- Воспроизводимость другим человеком: B = C > A (в B и C явно указаны места для источников/момента; A зависит от текста рядом с таблицей).
- Отсутствие смешения baseline и результата: C > B > A (в C отдельные колонки; в B — отдельные блоки; в A — одна таблица без явного разделения).
- Компактность: A > C > B.
- Соответствие текущему context.md и prompts.md: A = C = B (все сохраняют смысл и правила; вопрос только в оформлении).
- Отсутствие выдуманных чисел и требований: A = B = C (при условии не указывать несуществующие значения; для M2 — оставлять «по оценке студента» без авто‑пересчёта).

Итог: выбираем вариант C — таблица с отдельными колонками для baseline и результата после улучшения. Он устраняет риск смешения, остаётся достаточно компактным и сохраняет текущие правила/источники без выдуманных чисел.

## Предлагаемая версия раздела «Метрики» (вариант C)

```
## Метрики

Измеряем по сохранённым результатам запусков `results/P1-01.txt` и `results/P1-02.txt` и по оценке студента подтверждённости рисков. Правило подсчёта:

- M1: находка/риск учтён, если содержит путь к файлу и конкретное место (строки или функцию). Считаем вручную по тексту результата.
- M2: риск подтверждён, если его обоснование выводится из содержимого diff (изменённые строки или явно названное отсутствующее место). Если для подтверждения нужны сведения вне diff — риск не подтверждён и помечается статусом `possible`. Статус `possible` не учитывается как `confirmed`.

| Метрика | Baseline (P1-01) | После улучшения (P1-02) | Цель | Источники |
|---|---|---|---|---|
| M1: доля рисков со ссылкой на файл и место | 11/11 = 100% (по `results/P1-01.txt`) | Пересчёт по `results/P1-02.txt` | 100% | results/P1-01.txt, results/P1-02.txt |
| M2: доля рисков, подтверждённых входным diff | По оценке студента P1-01 (не пересчитывать автоматически) | По оценке студента P1-02 (не пересчитывать автоматически) | Присваивать `confirmed` только рискам, которые действительно подтверждаются diff; при недостатке данных риск явно помечается `possible` и не учитывается как `confirmed` | results/P1-01.txt, results/P1-02.txt; оценка студента |

Примечание: для воспроизводимости расчётов необходимо хранить и ссылаться на фактические файлы результатов (`results/P1-01.txt`, `results/P1-02.txt`).
```

- Применено: раздел «Метрики» в `practices/practice_01/problem.md` обновлён по варианту C; определения M1/M2, цель M2 и правила confirmed/possible не менялись.
