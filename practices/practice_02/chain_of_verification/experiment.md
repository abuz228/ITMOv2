# Chain of Verification

Файл ведёт OpenCode по вашим запросам. Агент записывает фактические результаты экспериментов и вносит изменения в связанные файлы. Свою оценку сообщайте ему в чате; вручную заполнять шаблон не нужно.

- Артефакт Практики 1: `practices/practice_01/problem.md`, раздел «Метрики».
- Модель: VseLLM / openai/gpt-5.
- Цель: проверить текущий раздел «Метрики» после RCTF и найти возможные неточности или непроверяемые утверждения.

## Запрос (Chain of Verification)

Сначала оцени текущий раздел «Метрики» в `practices/practice_01/problem.md` и предложи, что в нём стоит улучшить.
Затем составь вопросы для проверки своих предложений (например: можно ли однозначно посчитать M1/M2; не смешиваются ли `confirmed` и `possible`; есть ли источник для каждого текущего значения; не придуманы ли baseline/пороги; можно ли воспроизвести расчёт по указанным файлам).
Ответь на эти вопросы, используя только следующие источники: `practices/practice_01/problem.md`, `practices/practice_01/prompts.md`, `results/P1-01.txt`, `results/P1-02.txt`.
На основе проверки покажи исправленный вариант раздела «Метрики». Другие разделы не меняй.

## Результат проверки

1) Оценка текущего раздела «Метрики»

- Плюсы:
  - Чёткие правила подсчёта: для M1 требуется файл и конкретное место (строки/функция); для M2 — подтверждение строго по содержимому diff; `possible` не учитывается как `confirmed`.
  - Источники и момент измерения указаны (P1-01 → P1-02; источники — results/P1-01.txt, results/P1-02.txt и оценка студента для M2).
  - M2 baseline не придумывается моделью: текущие значения зависят от оценки студента.
- Замечания:
  - В таблице заголовок столбца «Текущее значение (P1-01)» подразумевает только P1-01, однако в строке M1 дополнительно упомянуто «P1-02: 3/3 = 100%», что смешивает базовое и последующее измерение в одном столбце.
  - Воспроизводимость расчётов зависит от наличия файлов `results/P1-01.txt` и `results/P1-02.txt`; описанная процедура подсчёта понятна, но в рамках проверки нужно опираться на фактические файлы результатов.

2) Вопросы для проверки

- Можно ли однозначно посчитать M1 по определению?
- Можно ли однозначно посчитать M2 по определению и без смешения `possible` и `confirmed`?
- Не смешиваются ли `confirmed` и `possible` в текущей формулировке?
- Есть ли источник для каждого текущего значения, указанного в таблице?
- Не придуманы ли baseline или числовые пороги?
- Может ли другой человек воспроизвести расчёт по указанным файлам?

3) Ответы на вопросы (использованы только: problem.md, prompts.md, results/P1-01.txt, results/P1-02.txt)

- M1: Определение однозначное (problem.md, раздел «Метрики»). Подсчёт ручной по тексту результатов. Число для P1-01 (11/11) заявлено, но для проверки требуется `results/P1-01.txt`.
- M2: Определение однозначное и исключает смешение с `possible` (problem.md). Текущее значение берётся по оценке студента, не пересчитывается автоматически — это соответствует требованию.
- Смешение `confirmed`/`possible`: В правилах явно написано, что `possible` не учитывается как `confirmed` — смешения нет (problem.md).
- Источники для текущих значений: указаны (results/P1-01.txt, results/P1-02.txt; оценка студента). Для чисел по P1-02 в строке M1 упомянуто «3/3 = 100%», но таблица обозначает столбец как «(P1-01)», что методологически некорректно — факт P1-02 лучше не указывать в этой ячейке.
- Придуманные baseline/пороги: отсутствуют. M2 baseline не числовой и привязан к оценке студента; числовых порогов не вводится (problem.md, prompts.md Практики 1).
- Воспроизводимость: при наличии `results/P1-01.txt` и `results/P1-02.txt` другой человек сможет воспроизвести расчёт по описанным правилам. Необходимость хранения и доступности этих файлов следует явно подчеркнуть.

4) Исправленный вариант раздела «Метрики» (предложение)

```
## Метрики

Измеряем по сохранённым результатам запусков `results/P1-01.txt` и `results/P1-02.txt` и по оценке студента подтверждённости рисков. Правило подсчёта:

- M1: находка/риск учтён, если содержит путь к файлу и конкретное место (строки или функцию). Считаем вручную по тексту результата.
- M2: риск подтверждён, если его обоснование выводится из содержимого diff (изменённые строки или явно названное отсутствующее место). Если для подтверждения нужны сведения вне diff — риск не подтверждён и помечается статусом `possible`. Статус `possible` не учитывается как `confirmed`.

| Метрика | Текущее значение (P1-01) | Целевое | Когда измеряем | Источник данных |
|---|---|---|---|---|
| M1: доля рисков со ссылкой на файл и место | 11/11 = 100% (по `results/P1-01.txt`) | 100% | P1-01 → P1-02 | results/P1-01.txt, results/P1-02.txt |
| M2: доля рисков, подтверждённых входным diff | По оценке студента P1-01 (не пересчитывать автоматически) | Присваивать `confirmed` только рискам, которые действительно подтверждаются diff; при недостатке данных риск явно помечается `possible` и не учитывается как `confirmed` | P1-01 → P1-02 → после правок v1.1 | results/P1-01.txt, results/P1-02.txt; оценка студента |

Примечание: для воспроизводимости расчётов необходимо хранить и ссылаться на фактические файлы результатов (`results/P1-01.txt`, `results/P1-02.txt`).
```
